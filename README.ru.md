# OpenIPC Camex

[English](README.md) | **Русский** | [简体中文](README.zh-CN.md)

[![Code size](https://img.shields.io/github/languages/code-size/OpenIPC/camex)](https://github.com/OpenIPC/camex)

Минималистичный UDP/TCP-туннель без внешних зависимостей для встраиваемых Linux-систем.

Поставляется в виде демона пользовательского пространства и опционального автономного модуля ядра.

---

## Возможности

- **Архитектура клиент/сервер** поверх UDP или TCP
- **Режим автоконфигурации** — клиент получает параметры туннеля от сервера
- **Протокол v2** — рукопожатие Noise (`NKpsk0`, X25519, ChaCha20-Poly1305,
  BLAKE2b), новые ключи на каждую сессию и направление, шифрование всегда
- **Без внешних зависимостей** — нужна только libc
- **Кроссплатформенная сборка** — x86_64, ARM, AArch64, MIPS (через CI)
- **Собственный модуль ядра** — `camex.ko` заменяет `tun.ko` и не имеет внешних зависимостей
- **Компактный код** — всего ~3 500 строк, легко провести аудит

## Быстрый старт

### Ключи

У сервера есть ключевая пара; каждому клиенту нужен **публичный** ключ сервера
и предварительный ключ (глобальный или свой `psk=` из конфигурации сервера).

```sh
(umask 077; camex --genkey > server.key)   # server_key=… (секрет) и public_key=…
```

### Сервер

```sh
sudo ./camex --mode server --port 5800 --config /etc/camex/camex.conf \
  --server-key-file server.key --psk secret
```

### Клиент (автоматический режим)

```sh
sudo ./camex --mode client --auto --name 0203A104B5AE \
  --server-host vpn.example.org --port 5800 \
  --server-pubkey <public_key> --psk secret
```

### Клиент (ручной режим)

```sh
sudo ./camex --mode client \
  --local-cidr 10.0.0.2/24 --gateway-ip 10.0.0.1 \
  --server-host vpn.example.org --port 5800 \
  --server-pubkey <public_key> --psk secret
```

### Android

Приложение подключается в автоматическом режиме: адрес, маршруты и MTU присылает
сервер.

| Главный экран                                  | Настройки                                      |
|------------------------------------------------|------------------------------------------------|
| ![Главный экран](docs/images/android-main.png) | ![Настройки](docs/images/android-settings.png) |

- **Server host / port** — сервер camex.
- **Client name** — ID клиента, то есть блок `[client ID]` на сервере.
- **Transport** — UDP или TCP, как на сервере.
- **Server public key** и **Pre-shared key** — `--server-pubkey --psk`; ключ
  должен совпадать с `psk=` клиента (или с глобальным ключом).
- **Route all traffic through the tunnel** — если выключено, через туннель идут
  только туннельная сеть и маршруты сервера.
- **Advanced** — MTU, keepalive и таймаут сервера
  ([скриншот](docs/images/android-settings-advanced.png)).

## Поддержка драйверов TUN

При запуске приложение автоматически определяет доступный TUN-бэкенд. Сначала оно пробует
`/dev/net/tun` (tun.ko); если это не удаётся или TUNSETIFF недоступен, используется
`/dev/camex` (camex.ko). С точки зрения протокола оба бэкенда работают одинаково.

Автоопределение можно переопределить параметром `--tun-dev <path>`:

```sh
sudo ./camex --mode client ... --tun-dev /dev/camex
```

| Возможность               | tun.ko (`/dev/net/tun`)                 | camex.ko (`/dev/camex`) |
|---------------------------|-----------------------------------------|-------------------------|
| Имя интерфейса            | динамическое (`tun0`, `tun1`, …)        | всегда `camex`          |
| Требуется ioctl TUNSETIFF | Да                                      | Нет                     |
| Внешняя зависимость       | `CONFIG_TUN=y` или загруженный `tun.ko` | загруженный `camex.ko`  |
| IPv4                      | Да                                      | Да                      |
| IPv6                      | Да                                      | Нет (только IPv4)       |
| Несколько экземпляров     | Да                                      | Нет (один)              |
| «Голые» IPv4-пакеты       | Да (с `IFF_NO_PI`)                      | Да                      |

## Приложение пользовательского пространства

### Режимы

| Режим    | Описание                                                             |
|----------|----------------------------------------------------------------------|
| `client` | Создаёт TUN-интерфейс и подключается к серверу                       |
| `server` | Принимает подключения множества клиентов и пересылает пакеты туннеля |

### Использование

#### Клиент

```sh
sudo ./camex \
  --mode client \
  --auto \
  --name 0203A104B5AE \
  --server-host vpn.example.org \
  --port 5800 \
  --server-pubkey <public_key> --psk secret
```

Клиент в ручном режиме:

```sh
sudo ./camex \
  --mode client \
  --local-cidr 10.0.0.2/24 \
  --gateway-ip 10.0.0.1 \
  --server-host vpn.example.org \
  --port 5800 \
  --route-cidr 192.168.100.0/24 \
  --server-pubkey <public_key> --psk secret
```

С явным указанием TUN-бэкенда:

```sh
sudo ./camex \
  --mode client \
  --local-cidr 10.0.0.2/24 \
  --gateway-ip 10.0.0.1 \
  --server-host vpn.example.org \
  --port 5800 \
  --server-pubkey <public_key> --psk secret \
  --tun-dev /dev/camex
```

#### Сервер

```sh
sudo ./camex \
  --mode server \
  --port 5800 \
  --bind-ip 0.0.0.0 \
  --config /etc/camex/camex.conf \
  --server-key-file /etc/camex/server.key \
  --psk secret
```

## Конфигурация сервера

Сервер читает плоский конфигурационный файл формата key=value, по одному блоку на каждого клиента.
Полное описание формата — в `examples/camex.conf`.

```sh
sudo ./camex --mode server --port 5800 --config /etc/camex/camex.conf
```

Клиенты в автоматическом режиме получают адреса из конфигурационного файла.
Клиент, для ID которого нет блока `[client ID]`, получает `[defaults]`, а если
адрес не задан — адрес из авто-пула `10.200.0.2`–`10.200.0.254` (занятые адреса
и адреса из блоков `[client ID]` пропускаются, адреса отключившихся клиентов
выдаются снова). Чтобы обслуживать только ID, перечисленные в файле, задайте
`allow_unknown_clients=no` в блоке `[server]`.

После изменения файла пошлите серверу `kill -HUP`. Работающий клиент в
автоматическом режиме получает изменённые адрес, шлюз, MTU или маршруты при
следующем рукопожатии (смена ключей, не позже чем через 10 минут, или
переподключение): он переоткрывает туннель с новыми настройками и заменяет
маршруты, без перезапуска.

## Модель безопасности

camex — небольшой туннель для камер, а не VPN общего назначения. Прежде чем
открывать его в недоверенную сеть, стоит понимать, что он защищает.

### Протокол v2 (camex 3.x)

- **Рукопожатие.** `Noise_NKpsk0_25519_ChaChaPoly_BLAKE2b`: клиент знает
  публичный ключ сервера, обе стороны знают предварительный ключ клиента.
  Каждая сессия получает новые ключи, отдельные для каждого направления (прямая
  секретность: утечка ключа не позволяет расшифровать записанные сессии).
- **Пакеты.** ChaCha20-Poly1305: данные шифруются, 17-байтный заголовок (тип,
  индекс сессии, счётчик) аутентифицируется, но остаётся читаемым. Пакеты, не
  прошедшие проверку, отбрасываются. Ключи обновляются каждые 10 минут.
- **Ключи.** Предварительный ключ задаётся готовым ключом (`hex:`, `base64:`) или
  парольной фразой, усиленной Argon2id. По перехваченному рукопожатию перебирать
  парольные фразы офлайн нельзя: для этого нужен закрытый ключ сервера.
- **Индивидуальные ключи.** `psk=` в блоке `[client ID]` даёт клиенту собственный
  ключ: он может зарегистрироваться только с ним, а глобальный ключ для этого ID
  больше не действует (если только обе парольные фразы не совпадают — тогда это
  один и тот же ключ). Точные правила — в разделе [Примечания](#примечания).
- **Адреса источника.** Клиент может отправлять пакеты только со своего
  туннельного адреса; пакеты с другим адресом источника отбрасываются.
- **Защита от повтора.** У пакетов данных окно на 2048 пакетов в каждой
  сессии. Пока у клиента есть живая сессия, рукопожатие со старой меткой
  времени отклоняется; повторённое рукопожатие не может перехватить рабочую
  сессию: новая сессия сменяет старую только с первым пакетом клиента в ней
  (клиент, у которого после перезагрузки часы ушли назад, всё равно
  подключится). Пакеты завершённой сессии нельзя подсунуть в новую: у неё
  другие ключи.
- **Роуминг.** Сессия находится по индексу, а не по адресу клиента: после смены
  адреса за NAT клиент сохраняет сессию.
- **Перезагрузка конфигурации.** После `SIGHUP` живая сессия, ключ которой
  удалён, изменён или теперь принадлежит другому клиенту, завершается.

### Что не защищено

- **Закрытый ключ сервера** позволяет его владельцу выдать себя за сервер перед
  клиентами, знающими предварительный ключ: храните `server_key` в секрете.
- **Метаданные.** Размеры пакетов, время, адреса сторон и открытая часть
  заголовка (тип пакета, индекс сессии, счётчик) видны.
- **Режима без шифрования нет**; для открытого туннеля без шифрования —
  OpenIPC VTesse.
- **Внутри туннеля** трафик не фильтруется: любой клиент может достучаться до
  сервера и других клиентов туннельной сети. Ограничьте это межсетевым экраном на
  туннельном интерфейсе сервера (`tun0` и т. п. с `/dev/net/tun`, `camex` с
  модулем ядра; имя сервер пишет в лог при запуске).

### Ограничения против отказа в обслуживании

- TCP-соединения, ещё не прошедшие рукопожатие, ограничены (4 с одного адреса,
  32 всего) и закрываются через 10 с. Рукопожатие несёт MAC на ключе из
  открытого ключа сервера: пакеты от тех, кто его не знает, отбрасываются
  после одного хеширования. Сервер обрабатывает не больше 200 рукопожатий в
  секунду.
- Сообщения в логе, которые может вызвать удалённая сторона (отброшенные пакеты,
  отклонённые регистрации), ограничены по частоте; число подавленных
  записывается в лог.
- Авто-пул выдаёт `10.200.0.2`–`.254` и никогда не отдаёт один адрес двум
  живым клиентам (адрес отключившегося клиента выдаётся снова; переподключённый
  клиент, в том числе после перезапуска сервера, получает свой прежний адрес,
  пока тот свободен);
  `allow_unknown_clients=no` обслуживает в автоматическом режиме только ID из
  конфигурационного файла (ручные клиенты ограничены своим ключом и адресом, см.
  [Примечания](#примечания)).

### Рекомендуемое развёртывание

- Файл ключа сервера должен быть доступен только серверу (`umask 077`);
  клиентам передавайте только `public_key`.
- Используйте готовые ключи (`hex:`/`base64:`) или длинные случайные парольные
  фразы.
- Дайте каждой камере свой `psk=` в блоке `[client ID]` и задайте
  `allow_unknown_clients=no`, когда перечислены все камеры в автоматическом режиме.
- Запускайте сервер только с нужными правами (`CAP_NET_ADMIN`; с модулем ядра
  ещё и доступ к файлу `/dev/camex`, см. ниже) и закройте туннельный интерфейс
  межсетевым экраном.

### Права модуля ядра

`/dev/camex` создаётся с правами `0600`, а `open()` требует `CAP_NET_ADMIN`; см.
[Ключевые архитектурные решения](#ключевые-архитектурные-решения). Модуль не шифрует
трафик: шифрованием занимается приложение в userspace.

### Приложение Android

Приложение использует `VpnService`, поэтому, пока туннель поднят, Android
показывает значок VPN; с `VpnService` его не убрать (клиент без TUN — #21). Через
туннель идут только туннельная сеть и маршруты, которые прислал сервер; маршрут
`0.0.0.0/0` от сервера игнорируется, если в настройках не включено **Route all
traffic through the tunnel**. Этот переключатель касается только IPv4: трафик
IPv6 через туннель не идёт.

## Модуль ядра

### Архитектура

```
Userspace                          Kernel
──────────────────                 ──────────────────────────────────────────
                                   ┌─────────────────────────────────┐
  write(fd, ipv4_pkt)  ──────────► │  copy_from_user()               │
                                   │  netif_rx(skb)                  │
                                   │       │                         │
                                   │       ▼                         │
                                   │  IP stack / routing             │
                                   │       │                         │
                                   │       ▼                         │
                                   │  camex_net_xmit()               │
                                   │  enqueue → rx_queue             │
                                   │  wake_up(rx_wait)               │
  read(fd, buf)        ◄────────── │  copy_to_user()                 │
                                   └─────────────────────────────────┘
  poll/select/epoll    ◄────────── wait_queue (rx_wait)

  /dev/camex  ←────────────────────────────────────── net interface "camex"
```

Два независимых объекта ядра — символьное устройство (`miscdevice`) и
сетевой интерфейс (`net_device`) — используют общий экземпляр
`camex_priv`. Обмен данными между ними идёт через очередь `rx_queue`,
защищённую `spinlock`.

### Ключевые архитектурные решения

#### 1. Отсутствие зависимости от `tun.ko`

Штатный `/dev/net/tun` — это отдельный модуль (`drivers/net/tun.c`),
который должен быть либо загружен, либо встроен в ядро. camex регистрирует
собственные `net_device` и `miscdevice` напрямую, используя только базовые
подсистемы ядра (`netdev`, `misc`, `skbuff`), которые **присутствуют всегда**
и не могут быть выгружены или отключены.

#### 2. `miscdevice` вместо ручной регистрации `chrdev`

`misc_register()` автоматически:
- динамически выделяет младший номер (без конфликтов);
- создаёт `/dev/camex` через udev/devtmpfs без каких-либо правил udev;
- выставляет права `0600` (только root).

`open()` дополнительно требует `CAP_NET_ADMIN`: устройство передаёт
пакеты в сетевой стек и отдаёт маршрутизируемый трафик, а это операция
администрирования сети, как и настройка tun-устройства.

Демону, который работает не от root с `CAP_NET_ADMIN` + `CAP_NET_RAW`,
нужен ещё доступ к файлу устройства, а `0600` его не даёт. Выдайте доступ
отдельной группе правилом udev (проверка capability при этом остаётся):

```sh
# /etc/udev/rules.d/90-camex.rules
KERNEL=="camex", GROUP="camex", MODE="0660"
```

или без udev, после каждого `insmod`: `chgrp camex /dev/camex && chmod 0660 /dev/camex`.

#### 3. Очередь пакетов под защитой `spinlock` + `irqsave`

`camex_net_xmit()` вызывается в контексте softirq (а не в контексте
процесса), поэтому для защиты очереди используется `spin_lock_irqsave`,
а не мьютекс. Это исключает взаимоблокировки при вызове из контекста прерывания.

#### 4. Блокирующий `read()` через `wait_event_interruptible`

Вместо активного ожидания или таймеров используется стандартный механизм
ядра: процесс засыпает на `wait_queue`, а `camex_net_xmit()` будит его
через `wake_up_interruptible()`. Сигналы корректно прерывают ожидание
(`-ERESTARTSYS`).

#### 5. Только IPv4 с явной проверкой в `write()`

При `write()` первый байт буфера проверяется ещё до `copy_from_user`
с помощью `get_user()`. Если версия IP не равна 4, возвращается `-EINVAL`
без выделения `skb` — так в стек не попадают мусорные пакеты или пакеты,
отличные от IPv4.

#### 6. Единственный пользователь (`EBUSY`)

`g_priv->attached` — `atomic_t`, который захватывается через `atomic_cmpxchg()`.
Если `/dev/camex` уже открыт, последующий `open()` сразу возвращает `-EBUSY`,
и два одновременных `open()` никогда не завершатся успехом оба. При `close()`
очередь очищается и слот освобождается под той же блокировкой, которую берёт
`camex_net_xmit()`, поэтому следующему `open()` не достаются старые пакеты.

#### 7. `ARPHRD_NONE` + `IFF_NOARP`

Интерфейс объявлен как не имеющий адреса канального уровня. Ядро
не пытается разрешать MAC-адреса (ARP) и не добавляет заголовки
Ethernet. Пользовательское пространство отправляет и получает **«голые»
IPv4-датаграммы**, начинающиеся с байта версии `0x45...`.

#### 8. Совместимость через прослойки на `#define`

Все условия `#if LINUX_VERSION_CODE` собраны в одном блоке `#define`
в начале файла. Тело драйвера использует только имена макросов
(`CAMEX_ALLOC_NETDEV`, `CAMEX_POLL_T`, `CAMEX_SKB_PUT` и т. д.) без
условной компиляции внутри функций. Это упрощает аудит и сопровождение.

### Совместимость с ядрами

| Диапазон      | Статус | Адаптированный API                                     |
|---------------|--------|--------------------------------------------------------|
| 3.10 – 3.16   | ✅     | `alloc_netdev(sz, name, setup)` — 3 аргумента          |
| 3.17 – 3.19   | ✅     | `alloc_netdev` + `NET_NAME_PREDICTABLE` — 4 аргумента  |
| 4.0  – 4.9    | ✅     | поля `min_mtu`/`max_mtu` отсутствуют в `net_device`    |
| 4.10 – 4.15   | ✅     | появились поля `min_mtu`/`max_mtu`                     |
| 4.16 – 4.19   | ✅     | `poll` возвращает `__poll_t`; константы `EPOLL*`       |
| 4.20+         | ✅     | `skb_put()` возвращает `void*` вместо `unsigned char*` |
| 5.x           | ✅     | изменения не требуются                                 |
| 6.0 – 6.6 LTS | ✅     | изменения не требуются                                 |

> **Примечание**: ядра 3.0 – 3.9 теоретически покрываются теми же
> прослойками, но на практике встречаются крайне редко (RHEL 6, ранние встраиваемые системы).

### Сборка и установка

#### Предварительные требования

```bash
# Debian / Ubuntu
sudo apt install linux-headers-$(uname -r) build-essential

# RHEL / CentOS 7
sudo yum install kernel-devel-$(uname -r) gcc make

# Fedora / RHEL 8+
sudo dnf install kernel-devel gcc make

# Alpine Linux
sudo apk add linux-headers build-base
```

#### Компиляция

```bash
make kmod
```

#### Загрузка модуля

```bash
sudo insmod camex.ko
```

Проверка:

```bash
dmesg | tail -5
# camex: loaded — /dev/camex <-> net:camex  (kernel 5.15)

ls -la /dev/camex
# crw------- 1 root root 10, 58 ...  /dev/camex

ip link show camex
# camex: <POINTOPOINT,NOARP> mtu 1500 ...
```

#### Автозагрузка при старте системы

```bash
# Установить модуль в дерево модулей ядра
sudo make kmod-install     # копирует camex.ko и запускает depmod -a

# Включить автозагрузку
echo "camex" | sudo tee /etc/modules-load.d/camex.conf
```

#### Выгрузка

```bash
sudo rmmod camex
```

> Выгрузка невозможна, пока `/dev/camex` открыт каким-либо процессом
> (`rmmod` возвращает `EBUSY`).

### API символьного устройства

| Операция                | Поведение                                                         |
|-------------------------|-------------------------------------------------------------------|
| `open()`                | Нужен `CAP_NET_ADMIN`; только один fd одновременно, иначе `EBUSY` |
| `read()`                | Возвращает один IPv4-пакет. Блокируется, если очередь пуста       |
| `read()` + `O_NONBLOCK` | Возвращает `EAGAIN`, если очередь пуста                           |
| `write()`               | Передаёт один IPv4-пакет в стек. Минимум 20 байт                  |
| `write()` не-IPv4       | Возвращает `EINVAL`                                               |
| `poll()`                | `POLLIN`, когда есть пакет; `POLLOUT` всегда                      |
| `close()`               | Очищает очередь, сбрасывает carrier, освобождает слот             |

#### Коды ошибок

| Код        | Причина                                               |
|------------|-------------------------------------------------------|
| `EPERM`    | `open()` без `CAP_NET_ADMIN`                          |
| `EBUSY`    | `/dev/camex` уже открыт другим процессом              |
| `ENODEV`   | Модуль выгружается                                    |
| `EMSGSIZE` | Буфер `read()` меньше длины пакета (пакет отброшен)   |
| `EINVAL`   | `write()`: размер < 20 или > 65535 байт, либо не IPv4 |
| `EAGAIN`   | `read()` с `O_NONBLOCK`, очередь пуста                |
| `ENOMEM`   | Не удалось выделить `skb`                             |

### Ограничения

#### Функциональные

- **Только IPv4.** IPv6 исключён намеренно. `write()` с IPv6-пакетом
  возвращает `-EINVAL`.

- **Только один процесс одновременно.** Держать `/dev/camex` открытым
  может только один файловый дескриптор. Повторный `open()` возвращает `EBUSY`.
  Для многопроцессных схем используйте мультиплексирование через Unix-сокет
  в пользовательском пространстве.

- **Единственный экземпляр устройства.** Создаётся ровно один интерфейс
  `camex` и одно устройство `/dev/camex`. Для поддержки нескольких экземпляров
  код нужно доработать: массив `g_priv[]` и суффиксы в именах.

- **Только TUN (уровень 3).** TAP (уровень 2, кадры Ethernet) не
  реализован. У интерфейса нет MAC-адреса (`ARPHRD_NONE`).
  ARP не работает.

- **Нет совместимости по ioctl с `/dev/net/tun`.** Команды
  `TUNSETIFF`, `TUNGETIFF`, `TUNSETPERSIST` и другие ioctl штатного
  драйвера не реализованы. Программы, использующие
  `ioctl(fd, TUNSETIFF, ...)`, без доработки работать с camex
  не будут.

- **MTU зафиксирован на 1500 байтах.** Изменение через
  `ip link set camex mtu N` ядро не блокирует, однако camex
  не проверяет MTU при `write()`.

#### Очередь и память

- **Глубина очереди — 64 пакета.** При заполнении новые пакеты молча
  отбрасываются, а счётчик `tx_dropped` увеличивается (виден в `ip -s link`).
  Значение задаётся константой `QUEUE_LIMIT` в исходном коде.

- **Каждый пакет в очереди хранится как `sk_buff`.** Каждый `sk_buff`
  занимает ~200 байт заголовка плюс данные пакета. При 64 × 1500 байт
  максимальный объём памяти под очередь составляет примерно 96–110 КБ.

- **`read()` со слишком маленьким буфером уничтожает пакет.** Если
  буфер меньше длины пакета, пакет теряется и возвращается
  `EMSGSIZE`. Всегда читайте в буфер размером не менее
  1500 байт (или MTU интерфейса).

#### Потокобезопасность

- Параллельные вызовы `read()` из нескольких потоков одного процесса
  не сериализуются на уровне fd — защищайте доступ мьютексом в
  пользовательском пространстве.

- Параллельные вызовы `write()` из нескольких потоков безопасны: каждый вызов
  независимо выделяет собственный `skb`.

#### Сеть

- **Маскарадинг/NAT «из коробки» отсутствует.** Чтобы маршрутизировать трафик
  из `camex` в интернет, настройте `iptables -t nat -A POSTROUTING`
  вручную.

- **`netif_rx()` против `netif_receive_skb()`.** Драйвер использует
  `netif_rx()` (более старый путь с отложенной обработкой в softirq). На
  высоконагруженных системах `netif_receive_skb()` даёт меньшую задержку, но
  требует контекста процесса или softirq — при необходимости замена тривиальна.

### Внутреннее устройство

#### Прослойки совместимости

Все условия `#if LINUX_VERSION_CODE` вынесены в отдельный блок `#define`
в начале `camex-k.c`. Тело драйвера использует только имена макросов
(`CAMEX_ALLOC_NETDEV`, `CAMEX_POLL_T`, `CAMEX_SKB_PUT` и т. д.) без
проверок версии внутри функций. Благодаря этому логика остаётся читаемой
и удобной для аудита.

#### Порядок регистрации и снятия регистрации

При `insmod`:
1. `alloc_netdev` + инициализация `camex_priv`
2. `register_netdev` → интерфейс появляется в `ip link`
3. `misc_register` → `/dev/camex` появляется в файловой системе

При `rmmod`:
1. `misc_deregister` → `/dev/camex` исчезает (новые вызовы `open()` блокируются)
2. `g_priv = NULL` → защита от use-after-free в пути xmit
3. `unregister_netdev` + `free_netdev`

Обратный порядок гарантирует, что к моменту освобождения памяти новые
обращения не смогут прийти ни по одному из путей (fd или netdev).

#### Carrier и состояние линка

- `netif_carrier_off` при инициализации — интерфейс показывает `NO-CARRIER`,
  пока пользовательское пространство не откроет `/dev/camex`.
- `netif_carrier_on` при `open()` — carrier становится активным.
- `netif_carrier_off` при `close()` — carrier сбрасывается; маршруты через
  интерфейс становятся недоступны.

#### `GFP_ATOMIC` в `xmit`

`camex_net_xmit()` вызывается в контексте softirq, где засыпать
запрещено. Поэтому `kmalloc` для `pkt_node` использует `GFP_ATOMIC`. Если
в этом контексте память недоступна, пакет отбрасывается
(`tx_dropped++`).

## Версионирование и процесс релиза

### Единый источник истины

**Единственное** место, где меняется версия ПО, — `src/version.h`:

```c
#define CAMEX_VERSION "X.Y.Z"
```

Все остальные упоминания версии (Android, CI, git-теги) **должны** совпадать с этим значением.
CI-конвейер проверяет это автоматически: релизная сборка завершится ошибкой, если
git-тег не совпадает с `CAMEX_VERSION`.

### Чек-лист релиза

1. **Поднимите версию в `src/version.h`** — обновите `CAMEX_VERSION`.
2. **Синхронизируйте версии Android** — запустите `scripts/sync-android-version.sh` (или `make apk`,
   который вызывает его автоматически). Обновляются:
   - `android/app/build.gradle.kts` — `versionName` + `versionCode`
   - `android/app/src/main/AndroidManifest.xml` — `android:versionName` + `android:versionCode`
3. **Коммит**: `git commit -m "chore: bump version to X.Y.Z"`
4. **Тег**: `git tag -a vX.Y.Z -m "Release vX.Y.Z"`
5. **Push**: `git push origin master && git push origin vX.Y.Z`
6. **CI автоматически создаёт GitHub Release** с артефактами вида
   `camex-X.Y.Z-<platform>`.

### Правила нумерации версий

- `versionName` (Android) = `CAMEX_VERSION` (например, `"2.3.6"`)
- `versionCode` (Android) = `MAJOR * 10000 + MINOR * 100 + PATCH` (например, `20306`)
- Git-тег = `v` + `CAMEX_VERSION` (например, `v2.3.6`)
- Заголовок GitHub Release = `camex vX.Y.Z`

### Ручной запуск CI

Если релиз нужно запустить вручную (например, чтобы заново загрузить артефакты),
используйте событие `workflow_dispatch` на вкладке Actions, указав во входном параметре
`version` имя тега (например, `v2.3.6`).

## Примечания

- Каждый клиент должен использовать уникальный IP-адрес в туннеле.
- Сервер пересылает пакеты по адресу назначения во вложенном IPv4-заголовке.
- Сокеты клиента только исходящие; на стороне клиента не открывается ни одного порта на прослушивание.
- В автоматическом режиме значения `-l`, `-g` и `-c` передаёт сервер.
- `examples/camex.conf` показывает формат базы параметров на стороне сервера.
- Протокол v2 работает поверх обоих транспортов — UDP и TCP; каждая сессия
  начинается с рукопожатия (`--server-key-file` на сервере, `--server-pubkey` и
  `--psk` на клиенте). camex 3.x не работает с camex 2.x.
- Сервер поддерживает индивидуальные PSK для клиентов: добавьте `psk=<key>` в блок `[client ID]`
  конфигурационного файла. Ключи привязаны к ID клиентов:
  - клиент, у которого есть свой ключ, может зарегистрироваться только с этим ключом;
  - глобальный ключ `--psk` действует только для клиентов без своего ключа;
  - ручной клиент со своим ключом может не указывать `--name`: его определяет ключ;
  - ручной клиент может занять только адрес `local_cidr` из своего блока
    `[client ID]` и никогда — адрес другого клиента, у которого есть свой ключ.
- Сервер принимает пакеты данных только от установленной сессии и только с
  собственным туннельным адресом клиента в качестве источника; пакеты с другими
  адресами источника отбрасываются.
